# ADR-003 — Cosmos DB Table API Persistence

## Status

Accepted

## Requirement Addressed

- REQ-AZ-008
- REQ-AZ-012

## Decision

Use Azure Cosmos DB Table API with serverless capacity for visitor-counter persistence.

## Alternatives Considered

### Azure SQL

Rejected because it introduces unnecessary relational database infrastructure for a single counter.

### Azure Table Storage

Not selected because Cosmos DB Table API is the approved persistence direction.

### In-memory Function state

Rejected because state would not reliably survive function restarts or deployments.

## Trade-offs

Advantages:

- Explicitly satisfies the persistence requirement.
- Serverless capacity aligns with low-volume workload.
- Persistent state survives application deployments.

Trade-offs:

- More infrastructure than an in-memory counter.
- Requires correct concurrency handling.
- Adds a database dependency.

## Consequences

The visitor counter becomes persistent infrastructure data.

Frontend/backend deployment must not recreate or reset the counter entity.


## OR-007 Persistence Resolution

The single logical counter record is updated as a concurrency-safe atomic logical increment:

```
read current count
→ atomically increment
→ persist
→ return resulting count
```

The implementation must prevent concurrent lost updates. Conditional entity updates/ETags with retry-on-conflict behavior are an implementation mechanism consistent with this decision; the observable invariant is that every successfully committed counter operation contributes exactly one increment.

**Requirement decision:** OR-007 is resolved.
